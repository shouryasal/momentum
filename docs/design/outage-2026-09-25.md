# Outage 2026-09-25 12:16Z → 2026-09-29 04:53Z: the host went to sleep

Forensic reconstruction of the gap between the last full cycle on 2026-09-25 and the
recovery on 2026-09-29. Sequel to the 2026-09-24 post-mortem in the `ops/healthcheck.py`
module docstring, which this document also corrects (see §7).

Everything below was read, never written: `~/earn-run` databases opened `mode=ro`,
container logs via `docker logs`, the WSL journal, `dmesg`, `/proc`, and the Windows
System event log (`Get-WinEvent`, no admin). Timestamps are UTC unless marked Gulf (+04).

## 0. Headline

The laptop lid was closed at **2026-09-25T12:16:43Z**. Windows entered Modern Standby,
woke for a few seconds roughly a dozen times, and at **2026-09-26T13:44:04Z** hibernated
("Standby Battery Budget Exceeded"). The lid was opened at **2026-09-29T04:52:55Z**. Between
those two instants the WSL VM, the two bot containers, cron, the console and every Earn
process were frozen, not dead, not restarted and not crashed. Nothing rebooted: neither
Windows nor WSL. The "WSL reboot at 2026-09-27 18:09" is a clock artefact (§3).

The system recovered by itself within nine minutes of the lid opening: cron fired at
04:55:07Z, the first ingest failed on WSL DNS, the second succeeded at 05:00Z, and ingest
cleared its own `data_stale` flag at **05:01:36Z**. The alerts said the right things at
04:55:07Z, the first second anything could run, but no alert design that lives on the host
could have spoken earlier, and none of the 20 alert rows written that morning was delivered
anywhere (`delivered=0`, no push channel configured). The self-recovery then produced a set
of self-inflicted false alarms and one lost decision slot that are still unfolding (§6).

## 3. Sleep vs reboot vs crash

**Sleep, then hibernate, for the whole gap. No reboot, no crash, on either side.**

- Windows: no Kernel-General 12/13, EventLog 6005/6006, Kernel-Power 41 or User32 1074
  after 2026-09-22T13:53Z; EventLog 6013 at 04:52:57Z reports uptime 572,355 s (6.6 days).
- WSL: one boot id since 09-22T23:04:38Z; `last -x` lists no reboot after 09-23 03:04 +04;

  the same processes before and after; both containers report `RestartCount 0` and

- The "WSL rebooted 2026-09-27 18:09 (uptime -s)" reading is false. `/proc/uptime` was
  140,663 s (39.07 h) at 09-29T05:10:49Z against a wall-clock span since boot of 150.10 h;
  the 111.03 h difference is exactly the host's sleep since boot per the Windows event log:
  09-23 05:13–07:42Z (2.46 h) + 07:42–13:22Z (5.68 h) + two ~1 min sleeps + 09-24
  06:23–20:36Z (14.22 h) + 09-25 12:16Z–09-29 04:53Z (88.60 h) = 110.99 h. WSL2's
  `CLOCK_MONOTONIC` does not advance while Hyper-V has the VM paused, so `uptime -s`,
  `dmesg -T` and `ps lstart` all print times shifted late by the accumulated sleep (`ps`
  shows the console "started" Mon Sep 28 20:55 +04; systemd says Fri Sep 25 04:19 +04 —
  the difference, 88.6 h, is precisely the 09-25→09-29 sleep). `dmesg` raw monotonic stamps
  confirm: `hv_utils: TimeSync` and `systemd-journald: Time jumped backwards, rotating` at
  each resume, three TimeSync lines at monotonic 139857–139878 s (05:01Z on 09-29).
- The 2026-09-24 "14-hour" outage was also a host hibernation (06:23Z–20:36Z, "Resume from
  Hibernate"), not a 14-hour wedge (§7).

## 4. The `LockBusy` in `logs/ingest.log`

Not a hung process, and not related to the sleep.

- `ops/lib/locks.py` takes `fcntl.flock(LOCK_EX|LOCK_NB)` on `ops/locks/ingest.lock`, a
  zero-byte file with no pid in it. A flock is kernel state on the open file description:
  it is released the instant the holder exits (or is killed by `timeout -k 30 600`), it
  cannot survive a reboot, and a suspended process keeps it for the whole suspension. There
  is no stale-pidfile failure mode in this design.
- The cron line guards with `flock -n ops/locks/cron-ingest.lock` first, so a cron ingest
  can only reach the Python `LockBusy` when the *other* ingest bypassed the cron flock,
  i.e. was started by hand (`python -m runs.ingest`). The console's job runner and the
  healthcheck reruns both use the same cron flock (`console/services/ops_service.py`,
  `Healthcheck._rerun_command`), so they cannot produce it either.
- Dating: `ingest.log` has no timestamps, but (a) the two tracebacks sit after the last
  `funding … 400 … PEPEUSDT` line (last cron funding-400 at 09-24T20:45Z) and before the
  `data_stale cleared` line of 09-29T05:01:36Z; (b) they cite `runs/ingest.py` lines 786
  and 822 for `with locks.acquire("ingest")`, two intermediate versions of the file — the
  deployed file has had it at line 865 since 09-25T01:44Z (mtime), so both events predate
  that; (c) `ingest_runs` for 09-24 21:00–22:00Z has seven off-grid windows (21:14:51,
  21:16:18, 21:28:15, 21:29:36, 21:30:38, 21:38:57, 21:40:08 — manual runs during the
  perp-discovery fix) and is missing exactly the two cron windows 21:15 and 21:30. The
  manual run 21:14:51–21:15:41 held `ingest.lock` when cron's 21:15:0x ingest started;
  the manual run 21:29:36–21:30:24 held it when cron's 21:30:0x started. Two collisions,
  each ≤ 50 s, 15 hours before the lid closed.
- The one lock that did span the sleep was the 09-25 12:15:02Z cron ingest, whose scanner

## 6. Alerts: what they said, when they could first have said it, and the false alarms

### 6.1 What was said, and to whom

At 04:55:07Z, the first second anything could run, healthcheck wrote twelve rows: `market
data stale (5320 min) — entries blocked` (critical); `advisory feed stale (funding 5320m,
news 5320m)` (warn); eight `<job> output missing for <slot> — reran once (detached, pid …)`
(warn); `AUTONOMY NEVER_RAN: No job has completed in 26h. The loop is not running.`
(critical); and the `TRADING IS BLOCKED` block: "market data is older than the gate allows
since 14:23 [Gulf], 1 entries refused … since 2026-09-26T10:23:52Z (2d 18h ago) … flag
data_stale set by healthcheck at 04:55:07Z … clears when: it expires at 06:55:07Z … stale
sources: book_snapshots, candles_1d, candles_1h, candles_4h, funding, news". Substantively
accurate, and the "clears when" line is what an operator needs.

Every one of the 20 rows written between 04:55Z and 05:11Z has `delivered=0`: `tg.send`
only delivers when `TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID` are present, and the product
decision is no Telegram. An alert here is a row in `ops_alerts` and an SSE event to a
console that nobody has opened since 09-25T09:15Z. The autonomy verdict was also wrong in
kind: the loop had not failed to run, the host had been asleep; "Press Start" is the wrong
instruction.

### 6.2 When they could first have said it

The host executed no instruction between 12:16:43Z on 09-25 and 04:53:01Z on 09-29 except
during the standby wakes, which lasted 1–80 s at minutes (:01, :05, :07, :08, :09, :23,
:31, :44, :46, :48) that never coincided with a `*/5` cron minute — so healthcheck did not
run once in the standby phase, and could not have. The first possible tick was 04:55:07Z
and it fired then. The last healthy tick was 12:15:02Z. Nothing that lives on this host
can shorten the 64h40m of silence: a sleeping host cannot alert.

The only designs that can reach a human on a sleeping host are external. `ping_deadman`
in `ops/healthcheck.py` (HEALTHCHECKS_URL, in the healthcheck allowlist) is exactly that:
a healthchecks.io check with a ~15 min grace would have emailed at about 12:30Z on 09-25.
Whether the variable is set could not be verified without reading `.env`; there is no
trace of a ping anywhere readable. A push channel for the 04:55Z alerts (Telegram or any
other) is the second half: the rows were right, they just went nowhere.

### 6.3 What the self-recovery did right

1. Ingest cleared `data_stale` itself at 05:01:36Z (`reconcile_staleness_flag`), 8m41s
   after resume and 3m after its first successful cycle, with healthcheck having re-armed
   the flag 88 s earlier. The expiry (`STALE_FLAG_TTL_MULT`) would have lifted it by
   07:00:08Z regardless. Both 09-24 remedies worked as designed.
2. The gate was fail-closed throughout the standby wakes: every entry attempted at 22:07,
   00:07–00:08, 10:09 and 11:31 was refused on `staleness` (data 11–48 h old); the SOL exit
   at 00:07:46Z was allowed, which is correct (exits are never blocked). The 24 h
   `flags.json` staleness rule would also have blocked entries from resume until the first
   flag write at 04:55:07Z.
3. The 12:15 ingest's locks survived the sleep and were released cleanly; no lock had to
   be removed by hand.
4. Bots reconnected on their own (ccxt websocket/REST fallback), no restart, no cap hit.
5. The console never died; `Restart=always` was not even exercised.
6. The missed-run reruns did restore the artifacts that are keyed on "at or after the fire
   time": ingest (`ingest_runs`), tca (`tca_state.last_run`), backup (`backup.stamp`),
   maintenance (`runs` row) — no false alarm from those.
7. The first healthcheck tick reported per-phase "last success 2026-09-25T12:15:02Z", which
   is the single most useful line for reconstructing this.

### 6.4 What it did not do, or did wrong

1. **`missed_run` is a flag nobody clears.** `check_missed_runs` is the only writer
   (`set_flag(... severity="info", expires_at=None)`); there is no `clear_flag("missed_run")`
   anywhere in `ops/`, `runs/` or `console/`. It is one key, so each new miss overwrites the
   reason and resets `set_at`: the `daily_review 2026-09-24T17:30:00Z` reason set at
   09-24T21:45:05Z (and re-set every 5 min until 12:15:02Z on 09-25) became `nav_job
   2026-09-28T20:10:00Z` at 05:10:07Z. It never expires, never blocks, and is listed in
   every daily digest as `flags: missed_run` for ever. That is why it "has been active
   since 09-25" — and it would have said so since 09-24T21:45Z had the reason not been
   overwritten.
2. **Daily jobs rerun on a later day can never satisfy their artifact rule**, so every
   multi-day sleep manufactures criticals about an hour after resume:
   - `nav_job`: rule `nav_daily.date_utc == fire date` (2026-09-28); `runs/nav_job` writes
     the date it runs (2026-09-29). "STILL missing" fired 05:10:07Z.
   - `daily_review`: rule `reports/daily/<Gulf(fire) − 1 day>.md` (2026-09-27 for the 09-28
     slot); `runs/daily_review.py` names the report `Gulf(now) − 1 day` (2026-09-28). Same
     mismatch produced the 09-24/25 storm: the 09-24T17:30Z slot wanted `2026-09-23.md`,
     the 20:40Z rerun wrote `2026-09-24.md`, and healthcheck shouted every 5 minutes for
     14.5 hours (207 incidents) about a report that existed under the other name.
   - `research_run`: rule `proposals/<Gulf(fire) date>-<slot>.json` (2026-09-28-1600);
     `_rerun_command` passes only the slot (`1600`) and `run_id_for`/`proposal_filename`
     use `now`, so the rerun wrote **today's** `2026-09-29-1600.json` at 05:01Z, seven
     hours early, from 3.7-day-old data, and the real 16:00 cron run will `return 0` on
     seeing it. Today's 16:00 decision has effectively already been taken as a stale
     abstain. The 09-28 slot still reads "missing".
   - `review_run`: rule `reports/review-<ISO week of fire>.md` (2026-W39); the rerun
     running now uses `self.now` (W40). Projected "STILL missing" ~06:55Z.
3. **The second research rerun was lost silently.** Healthcheck spawned reruns for two
   research slots five minutes apart; the second hit `flock -n` on the shared
   `cron-research.lock` and exited 1 into `/dev/null`. No `runs` row, no proposal for
   today's 08:30 slot, and `check_missed_runs` will not try again (`rerun_count` is
   already 1). The rerun path has no "lock busy — will retry" state.
4. **`TRADING IS BLOCKED` kept firing after trading was unblocked** (05:05:05Z, 05:10:07Z,
   with no flag and no stale source listed). `autonomy.acting()`'s `dry` test is "at least
   one wedge refusal since the last allowed entry and no allowed entry for `NO_ENTRY_MIN`":
   the last allowed entry is the 09-26T10:23:52Z LTC stake, the last refusal the 11:31:35Z
   staleness one, and no entry has been attempted since resume, so the verdict cannot
   change until a signal fires and the gate lets an entry through. `ops_state.
   trading_blocked_since` stays at 2026-09-26T10:23:52Z. The message also still says
   "since 14:23" — Gulf — while every other timestamp in it is UTC.
5. **Dedupe requires delivery.** `tg._deduped` only considers rows with `delivered=1`, so on
   a host with no push channel nothing is ever deduped: `trading_blocked` (TTL 60) was sent
   at 04:55, 05:00, 05:05 and 05:10; `missed2_daily_review_…` (TTL 24 h) went out every
   five minutes for 14.5 hours on 09-24/25. The storm is the same class of noise the
   healthcheck docstring warns about.
6. **"AUTONOMY NEVER_RAN"** is the wrong word for "the host slept 64 hours". The liveness
   view has no notion of host sleep; it cannot compare the wall-clock gap with the VM's
   awake time (`/proc/uptime` or `CLOCK_BOOTTIME` vs `CLOCK_MONOTONIC`) although the
   evidence is one syscall away.
7. **Reruns fire into a dead network.** The first tick after any resume spawns every missed
   job at once (nine here, including two 45–110 min LLM sessions) while WSL DNS is still
   down; the ingest rerun failed and its failure was quoted in the critical.
8. **Silence is still not detected off-host.** No evidence of a dead-man ping; no push
   channel; the console is read by a browser tab that has been showing 401 since 09-25.

## 7. Correction to the 2026-09-24 post-mortem

The healthcheck docstring says the `data_stale` flag "latched at 06:00:03Z, this watchdog
then stopped running, and the gate refused 655 consecutive entries over 14 hours with no
way back without a human". The Windows event log shows the host entered sleep at
06:23:21Z and resumed from hibernate at 20:36:41Z; `ingest_runs` and `gate_decisions` have
nothing between 06:23:25Z and 20:36:54Z. The gate refused entries for 18 minutes before
the sleep (06:05–06:23Z, 439 refusals) and 18 minutes after (20:36–20:54Z, 946 refusals
on `blackout:data_stale`), and the flag was cleared by ingest at 21:40:08Z once the
funding fix landed. The remedies adopted then (an expiring flag, ingest able to clear it,
`check_trading_blocked`) are sound and worked on 09-29; the narrative of a watchdog that
"stopped running" is wrong — the laptop was closed. Both outages have the same root cause.

## 8. Root causes

1. The runtime lives on a laptop whose lid was closed. Modern Standby freezes the WSL VM;
   the standby battery budget converts it to hibernation within ~25 h. No Earn process,
   timer or alert can run on a host that is not running. (Primary cause of the 64h36m gap.)
2. The system cannot tell "host asleep" from "loop dead", and says the latter. Every
   liveness and missed-run calculation is wall-clock-only.
3. Missed-run reruns of daily jobs are keyed on the fire slot for detection but on `now`
   for their output (nav_job date, daily_review day, research run_id/filename, review
   week), so a rerun after midnight or after a multi-day sleep can never clear its own
   alarm, and in research's case pre-empts the next real slot.
4. Alerting is a table plus a console. No delivery path exists off the host; dedupe is
   conditioned on delivery; the one external mechanism in the code (dead-man ping) is
   unverified.
5. WSL DNS lags Windows by 1–2 minutes after resume and ingest phases have no retry, so a
   rerun scheduled at T+2 min fails and is reported as a failing phase.
6. `missed_run` has no clearer, no expiry and a single key.

## 9. What to change (proposals, not yet done)

- Host: set lid-close to "do nothing" on AC and disable hibernate-from-standby for this
  machine, or move `~/earn-run` to an always-on host. Nothing in software substitutes.
- Off-host silence detection: confirm/enable `HEALTHCHECKS_URL` (dead-man) and a push
  channel for `critical` rows; make `_deduped` consider undelivered rows too.
- Add a host-sleep detector to `autonomy.liveness`: if the wall gap since the last
  heartbeat exceeds the VM's monotonic advance over the same span, verdict `host_slept`
  with the sleep window, not `never_ran`.
- Rerun policy after a resume: wait for a resolver/connectivity probe (or ~3 min) before
  spawning; retry a rerun whose `flock -n` lost; serialise reruns that share a lock.
- Artifact rules: derive each daily artifact from the same function the job uses to name
  its output (or pass the slot *date* to the job: `research_run 1600 --for 2026-09-28`),
  and make `research_run` refuse to write a proposal for a slot that has not happened yet.
- `missed_run`: expire it (e.g. 24 h), clear it when the artifact appears, and key it per
  job/slot so one miss does not erase another.
- `acting()`: end the `dry` verdict when the freshness sidecar is fresh and no blocking
  flag is active, independent of the gate streak; print Gulf and UTC consistently.
- Ingest: a bounded retry on `getaddrinfo`/connect failures inside `candles` and `books`.
- Rewrite the 09-24 narrative in `ops/healthcheck.py` to say the host hibernated.

## 10. Honest limits

- `powercfg /sleepstudy` needs an elevated prompt; it was attempted from this session and
  refused, and it is not available from WSL at all. Kernel-Power 506/507 undercount DRIPS
  exits: the bot logs and `gate_decisions` show wakes at 22:01, 23:00, 00:05 and 09:48 that
  the Windows log does not.
- The WSL kernel journal is not readable by user `shourya` (not in `adm`/`systemd-journal`),
  so resume instants inside the guest come from `dmesg` (monotonic, shifted) and from
  application timestamps. Guest wall-clock readings in the first seconds after a wake may
  lag by minutes until Hyper-V `TimeSync` corrects them (23:00 vs 23:12 above).
- `journalctl -b -1` is the 09-23 02:53–02:58 +04 boot and has nothing to do with this
  window; cron's own syslog lines are not visible to this user (only `crontab LIST`).
- `logs/ingest.log` carries no timestamps; the `LockBusy` dating is inference from the
  missing cron windows, the off-grid manual windows and the traceback line numbers. The
  runtime tree is not a clean checkout (362 modified files against `HEAD 927ec5c`), so the
  intermediate `ingest.py` versions cannot be tied to commits.
- Whether `HEALTHCHECKS_URL`, `TELEGRAM_*` or any push channel is configured is unknown:
  `.env` was not read. `delivered=0` on every alert row is consistent with none.
- The projected "STILL missing" alarms for research, daily_review and review_run after
  05:20Z, and the 16:00 `return 0`, are read from the code, not observed.
- `health.log` is empty because healthcheck prints nothing on success; the alert table is
  its only record.
- Nothing under `~/earn-run` was written; no container, cron, unit or console was touched.

## 11. Windows-side confirmation (added by the orchestrator, 2026-09-29 05:50Z)

The timeline above was reconstructed from inside WSL, which cannot read the Windows event
log. Read from Windows afterwards, the log confirms it independently and to the second.

**Power model.** `powercfg /a`: this hardware offers *Standby (S0 Low Power Idle) Network
Connected*, Hibernate and Fast Startup; S1–S3 are not supported. So the "sleep timeout:
never" setting on this machine (`STANDBYIDLE` 0 on AC and DC) protects nothing — closing the
lid enters Modern Standby regardless, and Hyper-V pauses the WSL VM while it is in it.

**Boot type (Kernel-Boot 27; `0x2` = resume from hibernate / fast startup):**

| UTC | boot type |
|---|---|
| 2026-09-23 13:22:49 | 0x2 |
| 2026-09-23 14:11:08 | 0x2 |
| 2026-09-23 14:19:28 | 0x2 |
| **2026-09-24 20:36:43** | **0x2** — the end of the "14-hour wedge": a hibernate resume |
| **2026-09-29 04:52:57** | **0x2** — the end of the 64-hour gap: a hibernate resume |

**Clock jumps (Kernel-General 1), which are the hibernation windows themselves:**

| resumed at | clock jumped from | dark for |
|---|---|---|
| 2026-09-24 20:36:41Z | 2026-09-24 06:23:30Z | 14 h 13 m |
| 2026-09-29 04:52:55Z | **2026-09-26 13:44:09Z** | **63 h 09 m** |

**Modern Standby transitions (Kernel-Power 506 enter / 507 exit):** cycles through 09-26
(10:23Z, 11:31Z, 12:46Z, 13:44Z), then no 506 event until 04:52:57Z on 09-29. The last exit
at 13:44:00Z on 09-26 was followed by the hibernation above with no logged entry — event
logging inside standby is lossy ("Connectivity state in standby: Disconnected, Reason:
Adaptive Connected Standby" at 12:46:21Z is the last thing written before the gap).

**What this closes.** §3's "sleep, then hibernate, no reboot, no crash" is confirmed on the
host side. The 111-hour discrepancy between `/proc/uptime` and wall-clock is the sum of these
hibernation windows. The two outages this system has had — 09-24 and 09-25→29 — share one
root cause: the lid. Nothing in the software failed first; the software's failures (a flag
that could not expire on 09-24, liveness that reads a paused clock as a dead loop, reruns
keyed on `now`) are what it did *after* waking, and §9 is about those.

**One nuance for §9 / the hosting document.** Disabling idle sleep is already done and did
not help. On this hardware the levers are: the lid-close action, the Modern Standby
battery/hibernate budget (`powercfg /q SCHEME_CURRENT SUB_SLEEP`: `HIBERNATEIDLE` is already 0
on AC but 2147483647 s on DC — the machine was on battery when it hibernated, or the
standby budget forced it), or a host that is not a laptop.
