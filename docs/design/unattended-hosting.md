# Unattended hosting: what it takes to run Earn 24/7

*Written 2026-09-29, the morning the laptop woke up after 3.7 days. Sequel to
[`outage-2026-09-25.md`](outage-2026-09-25.md) (the reconstruction) and to the 2026-09-24
post-mortem in the `ops/healthcheck.py` docstring, which the reconstruction corrected: that
"14-hour wedge" was also the host hibernating.*

## 0. The honest answer

The owner asked "can we start testing the app again and run trades automatically?" and then
said they would be away for eight hours. The answer is:

**Yes, the software runs itself. No, this machine does not stay on.** Earn's runtime is a WSL2
virtual machine inside a Dell Precision 7550 laptop. When the lid closes, Windows puts the
machine into Modern Standby and the VM is paused with it; if the battery budget runs out,
Windows hibernates. From 2026-09-25T12:16:43Z to 2026-09-29T04:52:55Z that is exactly what
happened: 88.6 hours of wall time during which the VM ran for a total of ~35 minutes in
seconds-long wakes. No bot, no cron job, no watchdog and no alert can run on a machine that
is not running, so the first warning about the silence was written the moment the lid opened
again, 64 hours late, and it was the wrong warning ("the loop is not running").

There are two ways to make "automatically" true, and one thing the system itself should
have said. This document gives all three:

- **Option A** — keep this laptop awake (free, ten minutes, still a laptop).
- **Option B** — move the runtime to an always-on host (€5–10/month or a one-off mini-PC).
- **The host check** — `ops/hostcheck.py`, so the system says *"this host slept for X hours
  in the last 7 days; unattended trading is not possible on it as configured"* instead of
  blaming the crontab.

Recommendation (section 4): do Option A today, before going live do Option B.

What always survives: the data. SQLite on ext4 inside the VHDX, WAL mode, `BEGIN IMMEDIATE`
writers; no database was damaged in either outage, and the risk gate stayed fail-closed on
staleness through every wake. What never survives: **the ability to say anything.** Alerts
are `ops_alerts` rows plus the console's SSE stream; there is no push channel by product
decision (no Telegram), and `HEALTHCHECKS_URL` (dead-man ping) is unverified. A host that is
asleep is indistinguishable, from the outside, from a host that is fine.

## 2. Option A — keep the laptop awake

Cost: nothing. Time: ten minutes in an **elevated** PowerShell. Result: the machine keeps
running with the lid closed on AC, WSL never idles out, Docker Desktop and the distro come
back after a reboot as soon as the owner signs in. What it does not fix: it is still a
laptop — unplug it, carry it, let the battery die, and Earn stops with no word.

Every command, what it does, and how to verify it:

```powershell
# ---- 1. The lid. THIS is the setting that was missing on 2026-09-25 and 2026-09-24.
#      0 = do nothing, 1 = sleep, 2 = hibernate, 3 = shut down.
powercfg /setacvalueindex SCHEME_CURRENT SUB_BUTTONS LIDACTION 0   # lid closed on AC: keep running
powercfg /setdcvalueindex SCHEME_CURRENT SUB_BUTTONS LIDACTION 0   # on battery too (optional; a flat battery still wins)
powercfg /setactive SCHEME_CURRENT                                  # apply
powercfg /query SCHEME_CURRENT SUB_BUTTONS LIDACTION                # verify: both indexes 0x00000000 (elevated shows it)

# ---- 2. Idle timers. Already 0 on this machine (verified); repeat for the record and for DC.
powercfg /change standby-timeout-ac 0
powercfg /change hibernate-timeout-ac 0
powercfg /change standby-timeout-dc 0        # optional: no idle sleep on battery either
powercfg /change hibernate-timeout-dc 0

# ---- 3. Hibernate / Fast startup. Two choices:
#   (a) keep hibernate available but stop the fast-startup half-hibernate on "Shut down":
reg add "HKLM\SYSTEM\CurrentControlSet\Control\Session Manager\Power" /v HiberbootEnabled /t REG_DWORD /d 0 /f
#   (b) remove hibernation entirely (also removes Fast Startup and the standby→hibernate path;
#       the cost is that a flat battery means a hard power-off instead of a resume):
powercfg /hibernate off
#   Verify either with:  powercfg /a

# ---- 4. What is holding the machine awake / what woke it (diagnostics, elevated):
powercfg /requests
powercfg /sleepstudy                          # writes sleepstudy-report.html; this needs elevation

# ---- 5. WSL: never suspend the VM for being idle. (There is no `wsl --manage` idle option in
#      WSL 2.6.3 - verified from `wsl --help`; the only knob is %USERPROFILE%\.wslconfig.)
#      The repo's script writes it, backed up, but it ALSO sets networkingMode=mirrored, which
#      changes what 127.0.0.1 means to the distro and moves the Ollama address the console has
#      probed (ops_state.ollama_base_url = http://172.29.64.1:11434). Prefer the minimal file:
@"
[wsl2]
vmIdleTimeout=-1
autoMemoryReclaim=gradual
"@ | Set-Content -Path "$env:USERPROFILE\.wslconfig" -Encoding ascii
#      Applies on the next VM start: `wsl --shutdown` (STOPS THE BOTS for ~1 min - do it in a
#      quiet minute, and only after step 6 exists so the distro comes straight back).
#      Or: powershell -ExecutionPolicy Bypass -File ops\windows\install-autostart.ps1 -WriteWslConfig  (mirrored networking included)

# ---- 6. Boot the distro at sign-in and hold it open, as YOUR user.
#      WSL distros are registered per Windows user (HKCU\...\Lxss). The repo's
#      ops\windows\install-autostart.ps1 registers EarnWSLKeepAlive under the SYSTEM account,
#      and SYSTEM has no "Ubuntu-24.04" - that task will fail with "There is no distribution
#      with the supplied name". Until the script is fixed, register the task by hand for the
#      signed-in user (runs at logon, restarts if it dies, never times out):
$act = New-ScheduledTaskAction -Execute "$env:WINDIR\System32\wsl.exe" -Argument "-d Ubuntu-24.04 -u shourya --exec /bin/sh -c `"exec sleep infinity`""
$trg = New-ScheduledTaskTrigger -AtLogOn -User $env:USERNAME
$set = New-ScheduledTaskSettingsSet -AllowStartIfOnBatteries -DontStopIfGoingOnBatteries -StartWhenAvailable -RestartCount 999 -RestartInterval (New-TimeSpan -Minutes 1) -ExecutionTimeLimit ([TimeSpan]::Zero) -Hidden
Register-ScheduledTask -TaskName EarnWSLKeepAlive -Action $act -Trigger $trg -Settings $set -RunLevel Limited -Force
Start-ScheduledTask -TaskName EarnWSLKeepAlive
Get-ScheduledTask -TaskName EarnWSLKeepAlive | Select TaskName,State     # verify: Running
wsl.exe --list --running                                                   # verify: Ubuntu-24.04
#      (A one-shot `wsl.exe -d Ubuntu-24.04 -u shourya -- true` at logon boots the distro too,
#      but exits, so the VM idles out 60 s later unless step 5 is in place. The sleep-infinity
#      form works with or without step 5.)

# ---- 7. Docker Desktop. It is a desktop app: it starts only in a signed-in session.
#      Settings > General > "Start Docker Desktop when you sign in to your computer" = ON.
#      Verify from PowerShell (both should agree; today they do not - see 1.2):
Get-ItemProperty 'HKCU:\Software\Microsoft\Windows\CurrentVersion\Run' | Select 'Docker Desktop'
(Get-Content "$env:APPDATA\Docker\settings-store.json" -Raw | ConvertFrom-Json).AutoStart
#      Settings > Resources > WSL integration > Ubuntu-24.04 = ON (verified ON: IntegratedWslDistros).
#      The containers are `restart: unless-stopped`, so the engine coming back brings them back.

# ---- 8. Windows Update: install on your schedule, never restart on its own.
#      Active hours are already 09:00-03:00 local (the maximum). Add the policies (Pro edition):
reg add "HKLM\SOFTWARE\Policies\Microsoft\Windows\WindowsUpdate\AU" /v NoAutoRebootWithLoggedOnUsers /t REG_DWORD /d 1 /f
reg add "HKLM\SOFTWARE\Policies\Microsoft\Windows\WindowsUpdate\AU" /v AUOptions /t REG_DWORD /d 3 /f   # 3 = download, notify to install
gpupdate /force
#      Then install updates by hand on a Sunday (the runtime has no Sunday-night job between
#      20:00 and 02:20 Gulf); check with:  Get-WindowsUpdateLog  or Settings > Windows Update.

# ---- 9. Stay signed in. Docker Desktop and the logon task need a session. Lock the screen
#      (Win+L) - do not sign out, do not shut down. If the machine must survive a reboot with
#      nobody there, enable automatic sign-in (netplwiz, untick "Users must enter a user name
#      and password") and add a lock-at-logon task; only acceptable with BitLocker on:
manage-bde -status C:                          # verify Protection On

# ---- 10. Verify the whole thing
powershell -ExecutionPolicy Bypass -File ops\windows\check-host.ps1      # the repo's read-only report
#      and in WSL:  python -m ops.hostcheck            (section 5) - it should read "kept_alive"
#      after the healthcheck has ticked twice with the probe wired in.
```

Trade-offs of Option A, honestly:

- **Lid-closed thermals.** A Precision 7550 with the lid closed on a desk is fine; in a bag
  it is not. The setting makes the laptop a server; the owner has to treat it as one.
- **Battery.** On battery, Modern Standby's budget still hibernates the machine. `LIDACTION`
  on DC = 0 only delays that. Unplugged means stopped.
- **Reboots need a person.** Windows Update and Docker Desktop both assume a signed-in
  session. Auto sign-in trades that for physical security, which BitLocker covers.
- **Wake timers are disabled** (`bd3b718a… = 0`). Leave them: a machine that never sleeps
  needs no waking, and a machine that does sleep is the problem, not the timer.
- **Alerts still do not leave the host.** `HEALTHCHECKS_URL` (a dead-man ping healthchecks.io
  turns into an email/SMS when it *stops* arriving) is the one off-host mechanism in the
  code; setting it is the only way a sleeping laptop is ever reported by something that is
  not asleep with it. That is a `.env` change the owner makes by hand.

## 3. Option B — an always-on host

A small VPS or a home mini-PC. The repo already assumes this shape: everything binds to
`127.0.0.1`, cron is generated, the console is a user unit with linger, the bots are a
compose project, Binance keys never leave `.env`.

### 3.1 What moves

| Thing | How |
|---|---|
| The checkout | `git clone` onto **ext4 under `$HOME`** (`~/earn-run`); `bash ops/setup.sh` for the venv. Never a synced or Windows path (`console/services/host_checks.check_onedrive` blocks that for a reason). |
| Data | `rsync -a` from the laptop **with the bots and cron stopped on the source** (or from `ops/backup.py`'s archive via `ops/restore.py`): `data/binance/*.feather`, `knowledge/earn.db`, `journal/journal.db`, `knowledge/universe/`, `knowledge/state/latest.json`, `proposals/`, `reports/`, `ft_userdata/` (the bots' own SQLite), `changes/`, `lessons*.md`. Copy `-wal`/`-shm` only when the writers are stopped, or checkpoint first. |
| `.env` | **By hand.** Type it or `scp` it from a machine you trust, `chmod 600`. It carries Binance keys and the console secret; it is never in a backup, a sync folder or a chat. |
| Docker | The **engine** (`docker.io` or docker-ce from the Docker apt repo), enabled in systemd. Not Docker Desktop. `config/earn.yaml: runtime.docker.runtime: engine` is what `host_checks.check_docker` already expects. `docker compose -p earn -f ops/docker-compose.yml up -d` recreates the containers; the bots' state is in `ft_userdata/`. |
| cron | `python -m ops.gen_ops_files --check` then `--install --yes` (renders `CRON_TZ=Asia/Dubai` and the `$E` root for the new host). `sudo timedatectl set-timezone Asia/Dubai` first, or `check_timezone` fails. |
| Console | `python -m ops.gen_ops_files --install-user-units` (user unit + `loginctl enable-linger`). It stays on `127.0.0.1:8765`. Reach it with `ssh -N -L 8765:127.0.0.1:8765 earn@host` and open `http://127.0.0.1:8765` locally. Nothing is exposed. |
| Ollama (local model) | A VPS has no GPU. `docs/design/local-model-choice.md` and `config/models.yaml` decide whether any chain needs it; on a VPS either run a small CPU model or let the chain fall through to Claude. A mini-PC can run Ollama exactly as the laptop does. |

### 3.2 What must NOT be copied blindly

| File | Why | What to do instead |
|---|---|---|
| `var/state/mode.json` | HMAC-signed with `EARN_CONSOLE_SECRET`. On a host with a different secret it fails verification and **every sleeve is TEST** — the safe default, and the right one for the first days on a new host. | Set the mode again from the console once the new host has run clean for a while. |
| `var/state/config.bless.json` | The protected-config digest is per checkout. | Re-bless on the new host via the console (`ops.lib.config_guard`). |
| Console token / auth state (`~/.config/earn/**`) | Per-host credentials. | Reissue; the setup wizard does it. |
| `var/runtime/**` | Generated overlays (mode, runtime, compose override) for **this** host's mode. | Regenerate: `python -m ops.gen_freqtrade_config`; the console's mode page writes the overlays. |
| `ops/locks/**`, `ops/killdir/KILL` | Locks are kernel state on the old host; a copied `KILL` file means the new host starts engaged (which is acceptable, but should be deliberate). | Start with an empty `ops/locks`; decide about `KILL` on purpose. |
| `knowledge/flags.json` | Carries `set_by`/`set_at` from the old host; the 24-hour staleness rule would block entries anyway. | Let the first `ingest` write a fresh one. |
| Autonomy heartbeats / state under `var/` | Would make the liveness view believe jobs ran on this host. | Start clean; `install_utc` in `ops_state` is stamped on the first tick. |
| `logs/` | Optional; the LockBusy tracebacks in `ingest.log` are from 09-24 manual runs and are not evidence of anything on the new host. | Start clean. |

Region: Binance spot API latency is irrelevant for a 1h-candle, spot-only, market-order-exit
system (hundreds of ms either way), so pick the provider, not the ping. Check the Binance
account's API key **IP restriction** before moving: whitelist the new host's static IP (a
security gain), and confirm the provider's country is one Binance serves — a UAE account
calling from Frankfurt is normal; from a restricted jurisdiction it is a locked key.

### 3.4 Security posture (the one the repo already assumes)

- Console on loopback only, reached through an SSH tunnel; SSH key-only,
  `PasswordAuthentication no`; `ufw default deny incoming; ufw allow OpenSSH`.
- `.env` mode 0600, owned by the earn user; Binance key with **withdrawals disabled** and
  IP-restricted; the same allowlist discipline (`ops/envwrap.sh`) as today.
- `unattended-upgrades` on, with `Unattended-Upgrade::Automatic-Reboot "false"` — the same
  rule as Windows Update: reboots are a person's decision.
- `ops/backup.py` to a second location (the laptop, or object storage) so the VPS is not the
  only copy of the record.
- Nothing else listens. `ss -tlnp` on the new host should show sshd and `127.0.0.1:8765`.

## 4. Recommendation

**Today: Option A, the minimal form** — steps 1 (lid), 5 (`.wslconfig`), 6 (keep-alive as
the user), 7 (Docker Desktop autostart) and 8 (no automatic restarts). It costs nothing, it
would have prevented both outages so far (both were lid-close → standby → hibernate), and
it keeps the paper record continuous while the owner is testing. Add `HEALTHCHECKS_URL` so
that silence is at least noticed by something outside the laptop.

**Before any sleeve goes live: Option B, a VPS first.** Not because the laptop cannot be
made to stay on — section 2 does that — but because a laptop's failure modes are human
(a lid, a bag, a cable, a battery, a Windows sign-in), they happen without a log line, and
the system's whole safety story is "the code refuses when the data is stale". That story
protects capital while asleep. It does not protect the *record*: 3.7 days of missing
decisions is 3.7 days the paper benchmark cannot be compared against, and going live on a
record with holes in it is going live without the evidence the design demands. A VPS
removes the human failure modes for €5–10 a month, is reproducible from this document in
an afternoon, and is monitored by someone whose job it is. A mini-PC is the right answer
if Ollama matters or the Binance IP must stay in the UAE; it inherits home power and ISP.

Either way the host check in section 5 belongs in the healthcheck first: a system that
cannot tell "the host slept" from "the loop died" will misdiagnose the next outage on any
host.

## 5. The host check: `ops/hostcheck.py`

A new module, kept out of `ops/healthcheck.py` so it can be wired with one line and tested
alone. It answers three things and says one sentence.

**What the host is** (`hostcheck.host_facts()`): WSL2 or not (`/proc/version`), distro
(`WSL_DISTRO_NAME`), `/etc/wsl.conf [boot] systemd`, systemd as PID 1, `loginctl` linger for
the user, `.wslconfig vmIdleTimeout` when the file is reachable, `boot_id`. Every probe that
cannot be read is `None`, never a guess.

**Whether it slept** (`hostcheck.suspend_windows()`), from three sources:

1. `ops_incidents` rows with `kind='host_suspended'`, written by
   `Healthcheck.check_host_suspend` as `from <iso> to <iso> (3d 16h); data 5320 min old at
   resume; …`. The reader takes the two ISO stamps as the truth and ignores the humanised
   words; it also accepts JSON (`from`/`to`, `hours`/`minutes`/`gap_min`). An incident with
   no derivable length is dropped, not guessed.
2. The watchdog's own tick-gap windows (`ops.lib.suspend`, `ops_state.host_suspend_windows`,
   stamped from `ops_state.healthcheck_last_tick_utc`): the same sleeps, kept even after an
   incident is closed. A tick gap cannot tell "the VM was paused" from "cron did not run the
   healthcheck", which is what the third source is for.
3. Its own **clock probe** (`hostcheck.record_tick()`): WSL2's `CLOCK_MONOTONIC` stops while
   Hyper-V has the VM paused (that is why `uptime -s` reported a "reboot" on 2026-09-27 that
   never happened — 111 h of hidden time on this VM as of this morning). Each tick persists
   `(wall, monotonic, boot_id)` in `ops_state.hostcheck_clock_probe`; the next tick's
   `Δwall − Δmono` above 120 s is a sleep, recorded in `ops_state.hostcheck_suspend_gaps`
   (pruned to 7 days). A changed `boot_id` is a real VM reboot and is recorded as such. A
   tick gap with **no** monotonic drift is not a sleep — it is a watchdog that did not run.

Overlapping windows merge, keeping the longer; the `ops_state` keys of the two detectors
are distinct and neither writes the other's.
